# 算邻办公室现场验证计划

## 验证目标

核实两件事：办公室是否存在需要多机分担的事件处理瓶颈；在真实设备和网络条件下，联合调度是否相对简单策略带来可以解释的收益。允许得到无明显收益或单机更合适的结果。

## 需求访谈

邀请不少于3位实际承担巡检、办公室管理或设备维护工作的人。先告知仅用于参赛研究、可以拒绝记录，不收集身份凭证和敏感场地细节。不要先展示希望达到的提升数字，以免诱导。

逐一询问：现在事件如何进入系统、一天大约多少条、什么时候集中到达、什么情况会超时、超时影响是什么、现有电脑为何无法处理、哪些数据不能流转、谁能确认分类结果、愿意维护几台设备、试用后是否认为值得。请受访者举一个真实的最近案例，确认使用其匿名反馈的许可。

记录访谈日期、匿名编号、角色、原始表述、允许引用范围和后续联系许可。没有许可时不录音或拍摄。汇总“支持需求”和“反对需求”的证据，不能只摘录正面反馈。空白记录表为模板，不是已取得证明。

## 物理设备与组网

至少两台真实电脑，使用团队有权限使用的网络。记录设备编号A/B/C、CPU、内存、操作系统、供电、Wi-Fi或有线、Python版本、代码哈希、后台负载。协调端执行LAN启动，其他电脑运行worker。初始保持相同模型，核对输出一致。

拍一张能同时看到设备A/B和界面的照片；避免拍到单位名称、徽标、人脸、门禁密码和内部文档。视频中同步说明实际终端数。通过IP连接不能单独证明两台物理机器，因此设备表、全景照片与原始任务记录应相互对应。

## 数据准备

独立准备至少100条去标识事件，由两人标注；有歧义的事件保留并人工协商。原始内容在获得许可前不进入系统。真实数据稀缺时继续使用合成文本，但保持“合成”标签。

用于模型质量的测试集与训练集按来源或时间划分，不能只是替换同一模板中的几个词。报告四类混淆矩阵、每类召回率、宏平均F1和人工复核比例。无真实标注集时不填准确率。

用于调度比较的同一份任务文件应包含事件内容、提交顺序、时限、范围、负载循环数和输入哈希。所有策略使用完全相同输入。模型本身与人工CPU循环分开计时、分开报告。禁止把人为放大的负载当作真实AI模型耗时。

## 实验设计

每策略至少5轮，每轮100项任务。四种策略顺序轮换；每轮先预热，并等待上一轮结束。保持设备、电源与模型一致。正常办公低负载、集中突发、快节点受到后台占用和执行端断连四类条件分别运行，记录真实变化方式。

断连实验中，先让一个执行端领取任务，记录任务ID，再关闭该worker或断开其网络。等待租约到期，查看重排事件，确认其他可用节点完成。重新送达旧租约结果应被拒收，不能覆盖新结果。录屏保留时间与任务ID；不使用系统全局断网或影响其他人的网络。

带宽限制只有在明确配置了实验链路、知道作用范围且不影响他人时执行；记录限制工具、配置、持续时间与撤销方式。如果仅更改系统内的bandwidth参数，应描述为“估计参数变化”，不能说实际链路已限速。

## 指标和统计

按时完成率以全部提交任务为分母；失败、取消、未完成单独列出。完成时延使用协调端时钟，无需同步执行端墙钟。均值与P95同时报告，P95使用最近秩法。成功任务时延不包含失败，必须同时报告失败数，不能让失败导致均值看似改善。

每轮作为一次统计单位；报告各轮原始结果和均值，样本较小时给区间或明确不确定性。对照差异按每轮配对计算，避免对数百个相关任务直接做独立样本显著性检验。只有发生独立多机测试后才填写多机提升比例。

## 输出与验收

保存设备表、网络图、输入文件与哈希、逐任务CSV、逐轮汇总、结果截图、断连录像、匿名反馈与授权范围。生成测试报告时注明地点类型和日期，公开材料删除所在单位与教师信息。

验收条件是“任务真实执行、输入相同、记录完整、失败不丢失、结论不超出证据”。效果不好时记录失败原因，说明瓶颈或适用条件，必要时调整场景，不改数据来迎合目标。
