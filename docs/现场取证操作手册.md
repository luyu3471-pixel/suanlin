# 算邻现场取证操作手册

本手册配合2026年10月27日新增的现场取证工具使用。以下人数、样本量与轮次为便于两人团队实施的建议，不是官方最低要求。目标是形成可核对的需求、设备、任务与模型证据，不预设实验必须胜出。

## 从哪里开始

按两台Windows电脑、同一可信局域网、每天约1小时安排。先完成需求访谈与双机接通，再跑对比，最后做模型质量与受控故障验证。现有小文字模型可能根本不需要多机加速；只有真实业务存在计算瓶颈，后续才有理由接入更重的实际模型。不要以人工CPU负载代替业务需求。

在电脑A的项目目录执行：

```powershell
cd D:\6G
python tools/field_evidence.py init
```

空白访谈、设备和事件表位于 `.local/field-evidence/records`。直接把这个路径粘贴到资源管理器地址栏即可。工具不填入任何受访者、真实事件或设备配置。已有表格不会覆盖。

所有新增原始记录保存在 `.local/field-evidence`，会被现有打包工具排除。它们可能包含尚未去标识的文本、主机信息和原话，需人工审核后选择公开部分。不要直接把整个.local文件夹上传。

## 需求证据怎么取得

找3位实际承担办公室管理、巡检或设备维护的人，各聊10至15分钟。由一人提问，另一人记录；先询问是否同意匿名记录和引用，录音或拍照另行取得同意。不用先介绍希望获得的性能提升数字。

可以这样开场：“我们在做一个让几台电脑分工处理AI任务的实验，想了解你们有没有实际处理瓶颈；如果没有也请直接说。可以记录匿名意见吗？”

重点问：现在有哪些事件、用什么工具、每天多少条、最近一次来不及处理发生在什么时候、慢在人工还是计算或网络、目前有没有真的在运行AI模型、等待多久会影响工作、哪些设备和数据可以参与协作。请对方举具体事例；若没有计算瓶颈，就把“没有”如实记下来。

保存原始记录、经许可的历史日志或去标识截图、可公开的原话和授权范围。访谈表里的每项内容由实际参与人填写。需求证据证明用户遇到了什么问题，不直接证明算邻解决了它。

## 两台真实电脑怎么接通

电脑A作为协调端，同时只启动一个本机执行进程；电脑B启动一个远程执行进程。这样共有两台物理电脑、两个正常执行节点。

先关闭之前运行的算邻窗口，避免占用8765端口。在A的项目目录启动：

```powershell
python launch.py --host 0.0.0.0 --workers 1 --data-dir .local/office-field
```

保持这个窗口开着。浏览器在A访问 `http://127.0.0.1:8765`。另开一个PowerShell窗口运行 `ipconfig`，记录正在使用的网卡IPv4地址。下面以 `192.168.1.100` 举例，实际操作必须换成你们A的地址。

把更新后的完整交付包解压到B，找到包含launch.py的那层目录并在其中打开终端；B也安装Python 3.10或更新版本，不需要安装第三方运行库。通过可信方式将A的 `.local/office-field/access_token` 文件本身复制到B，命名为 `token.txt`，保存在B的项目目录。令牌不放进公开材料。

在B执行以下整行命令：

```powershell
python -m suanlin.worker --coordinator http://192.168.1.100:8765 --token-file token.txt --name 办公室电脑B --id office-b
```

在A的“算力节点”页核对B，点击“设为可信”。两个正常节点ID应为 `local-1` 和 `office-b`，均在线且接收任务。远程连接不自动证明两台物理机器，所以还需完成设备表与照片。

连接失败时，检查A的IP、B所在网络和A是否允许Python在专用网络接收入站连接。部分校园或访客Wi-Fi会隔离终端，可以使用团队有权管理的可信实验网络；不需要关闭整个防火墙。普通HTTP不适合直接暴露到公共互联网。

## 拍什么和记什么

在设备表填写A/B、对应节点ID、实际型号、CPU、内存、系统、Python版本、网卡类型、供电方式和后台负载。在各电脑的“设置—系统—系统信息/关于”查硬件系统信息，在终端运行 `python --version` 查版本；记录你们实际使用的系统页面名称即可。

拍一张同时看见两台物理电脑的全景，再分别拍A的节点页和B的运行终端，照片中能对应A/B和节点ID。录一段短屏幕视频，展示提交任务、分配、查看结果。拍摄前避开姓名、所在单位标识、指导教师、个人信息、令牌和内部文件。

性能测试时停止录屏、下载和其他测试，避免把拍摄负载掺进对比。取证照片和功能录像可以在性能轮次之前或之后完成。

## 公平对比怎么跑

先跑合成事件、无附加CPU负载的功能对比。在A另开PowerShell，进入项目目录执行：

```powershell
python tools/field_evidence.py run --use-demo
```

默认固定、轮询、随机和联合四策略各5轮，每轮20项，共400项正式任务；另有4项预热，不进入正式统计。不同策略在同一轮使用相同输入与提交间隔，策略顺序轮换。固定基线明确使用A的 `local-1`。

每次结果放在 `.local/field-evidence/runs/日期时间-comparison-随机编号`，不会覆盖原来的本机基准，也不会覆盖上一轮现场结果。该目录的 `summary.md` 可以阅读；`summary.json`、`trials.json`、`tasks.csv`、逐轮完整结果与输入文件用于核查。原始节点信息也会保存。重复调度8条合成文本400次，不等于400起真实事件。

同一实验默认完成时限为5000毫秒；应在实验前根据业务需求确定时限，不能看完结果后再挑一个最有利于自己的值。低负载和连续提交可以分别测试，但要保存每次的条件与完整结果。

以下附加负载测试仅用于研究排队，报告会明确标为人工CPU负载，不能写成实际巡检收益：

```powershell
python tools/field_evidence.py run --use-demo --compute-loops 200000 --note 人工CPU负载下的双机功能与排队实验
```

至少查看完成数、按时率、均值、P95、失败数和每个节点实际完成的任务数。所有策略都满足时限、联合策略没有获胜、或B没有分到任务，都应如实保留。不要删除不利轮次，只展示最漂亮的一次。

工具默认要求观察到远程连接才做现场流程。`--allow-same-host-test` 仅给开发工具自测使用，不用于你们的物理双机证据。

## 真实事件与模型质量怎么取证

在 `records/事件标注.csv` 填写真实取得许可的文字记录。先做20至30条试评，条件允许再扩充至100条以上。每行含文本text、最终人工标签label、来源source、日期和两人的独立标签。四种合法标签为“烟雾风险”“通道占用”“门禁异常”“正常状态”。来源填写“真实观察”“授权历史”“受控模拟”或“自编合成”，不要混写。

用Excel或WPS填写后，另存为“CSV UTF-8”，避免普通CSV使用其他编码而无法读取。表头保留原样，带英文逗号的文本交给表格软件正确引用。空白表不自动生成样本。

真实异常记录优先取经许可的历史材料。没有某类样本时如实缺失；不为了凑样本制造危险情形。自编或模拟事件可以帮助功能测试，但要保留来源标签，不能变成真实案例。

两人先独立判断标签，再讨论分歧，确定label后才运行模型。不能先看模型答案再反过来填人工标签；测试事件不要用于继续修改训练集后又当成独立测试。

在A运行：

```powershell
python tools/field_evidence.py evaluate --events-csv .local/field-evidence/records/事件标注.csv
```

工具生成准确率、各类召回率、已覆盖类别的宏平均F1、混淆矩阵、错误例、重复数量与训练集完全重合数量。缺少的类别没有质量证据，分数不是应用认证。来源是你们记录并负责核实的，程序不能替你们证明授权或事件真实。

取得足够事件后，可以用同一份表跑真实事件任务对比：

```powershell
python tools/field_evidence.py run --events-csv .local/field-evidence/records/事件标注.csv --tasks 100 --rounds 5 --note 经许可的文字事件任务对比
```

即使输入是真实事件，仍需说明测试到达过程是实验脚本控制的，不能称为已经连续上线运行的真实业务流量。

## 受控进程中断证据怎么取得

该实验测试“一个执行进程退出后任务能否转交其他节点”，不测试无线掉线、整机断电或真实故障率。它只使专门的故障端退出自身，不关闭其他程序或网络。暂时停止其他任务提交，先跑完性能对比。

B的正常worker可以继续开着。在B另开一个项目目录终端执行：

```powershell
python tools/fault_worker.py --coordinator http://192.168.1.100:8765 --token-file token.txt
```

A会多出 `office-b-fault`，它与 `office-b` 同属物理电脑B，不能算作第三台电脑。在A核实后把这个专用故障端设为可信，再启动屏幕录像并执行：

```powershell
python tools/field_evidence.py failure
```

工具会暂时暂停其他正常节点接收新任务，确保测试任务先由故障端领取，再恢复A作为接替端。故障端收到任务后按预设退出，B的该窗口会显示预期退出说明和退出码73。等待约25秒租约到期后，观察任务是否由A接手完成。工具最后恢复原先调整过的节点设置；断开协调端可能导致恢复失败，此时需在节点页检查。

本次目录为 `日期时间-process-failure-随机编号`。保存 `timeline.json`、`result.json`、`node-restore.json` 和屏幕录像。只有实际观察到目标端领取、至少2次派发、指定接替端完成时，结果才为passed。普通完成或超时会如实记录为未形成该恢复证据，不会自动写成功。

这段故障录像与时间线应对得上同一个任务ID。退出码73是本实验预设的受控退出，不是把软件缺陷包装成真实设备故障。

## 最后公开哪些材料

公开材料建议包括：匿名需求汇总、经同意引用的原话、去标识设备表和全景照片、四策略全轮次结果、一个按任务ID可回溯的受控故障案例、模型质量与失败例、适用条件和限制。

原始记录留在本地，不直接公开完整.local目录。人工删除或遮挡身份、单位、教师、令牌、主机信息和敏感业务内容后，再把允许公开的结果整理进佐证PDF。将真实观察、授权历史、受控模拟、合成数据和仿真分开写，注明每类证据支持的结论。

没有拿到需求或真实负载收益时，仍可如实提交设计方案与原型验证。不要把“设备接通了”替代为“已经为办公室提升效率”。

本次新增工具、模板与手册由生成式AI辅助制作。工具检查在同机环境进行，只验证工具行为，不算作你们实际完成的用户访谈、物理双机或6G验证。
